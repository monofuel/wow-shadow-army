# Quest completion QA loop — 2026-08-15

Ticket `../tickets/in-progress/0057-quest-completion-qa-loop.md`. Goal: prove
the bots can finish quests end to end — accept, objective progress, complete,
turn in, reward, next — unattended, and fix what stops them.

Scenario seat: **Kaisel**, undead warlock, account `shadow9`, guid `1000012`,
rolled fresh in Deathknell. Not one of the four home seats; own runtime tree
(`local_data/qa-seat/Kaisel/`), own debug port (`7800`). The home seats and
Murist were never touched: no reload, no teleport, no GM progress of any kind.

## Standing up the seat (two things that are broken in-repo)

**1. Every `*-account` Makefile target is dead.** They shell out to
`server/scripts/manage_coworld_accounts.py` in the upstream checkout; upstream
no longer has a `server/` tree at all, so `make warlock-account`,
`igris-account`, `tusk-account`, `beru-account`, `soap-account` and the
human `account` target all fail with `can't open file ... manage_coworld_accounts.py`.
Replacement used here: the VMaNGOS GM console over SOAP, wrapped as
`tools/soap.sh` (`tools/soap.sh account create <user> <pass>`). The existing
targets are left alone — repointing them is a separate change.

**2. The seat launch path cannot roll a character.** `docs/warlock-seat.md`
records that a missing `--character-name` is created by `connectBotControlSession`
via `CMSG_CHAR_CREATE`; that was the `--scenario=nim-control` reference-player
route, which upstream has since removed ("Unsupported Reference Player
scenario: nim-control"). The surviving CLI world-entry route
(`player/runtime/glue_connect.nim` `startConnect` →
`environment/client/world_sessions.nim` `requireExistingCharacter`) hard-fails
on an unknown name. Setting `VANILLA_WOW_PLAYER_CHARACTER_CREATION=1` does not
help — that env is read by `player/reference_player/player_runtime.nim`, a
different entry point.

What does work is the **GlueXML managed-character route**: omit
`--character-name` (that missing CLI field is exactly what turns the front door
on, `gluexml_runtime.nim` `glueRuntimeUsesFrontDoor`) and pass
`--create-character-name/-race/-class/-gender`. With `--controller=embedded`
the front door then self-drives login → realm → create → enter world
(`glue_connect.nim` `driveGlueCharacterSelectAutoAdvance`). Captured as
`make qa-character`; the ordinary run is `make qa-seat-start` with
`--character-name`, identical in shape to `launch_home_seat`.

The `seat` lease has capacity 5 (`agents/agent_lease.py` `SHARED_CAPACITIES`).
Four home seats plus a traverse race-league client filled it, so the QA seat
queued for ~8 minutes before entering the world. Nothing was killed to make
room.

## Baseline run

Kaisel entered the world at the Deathknell crypt (1676, 1677) at 06:52 UTC and
ran `--lua-entry home` (which is `accelerated` with `set_quests(true)` — the
same brain the four home seats run).

_(baseline observations, failures and fixes recorded below)_

## Failure 1 — a reward choice is never selected, so no turn-in completes

**Symptom predicted from the code, confirmed by the DB:** across every seat,
the only quest ever `rewarded=1` by a bot is `1470 Piercing the Veil`
(Shadowfel, Igris). Every quest the bots are sitting on that has a reward
*choice* is stuck.

**Cause.** `lua/entry/accelerated.lua` answered the reward panel with a bare
`/questreward`. The client rejects that when the quest offers a choice and
nothing is selected:

```nim
# environment/client/quests/updates_and_commands.nim questRewardCommand
elif questFrame.selectedChoiceKnown: choiceId = questFrame.selectedChoiceId
elif questFrame.choiceItems.len > 0:
  return commandError("Choose a quest reward first.")
```

`commandError` sends nothing. The panel stays open, the brain re-issues the
same verb next tick, and the quest never completes. `1470` turned in only
because it has no `RewChoiceItemId1`. Of the Deathknell/Tirisfal starter
quests, `358, 364, 376, 380, 381, 382, 3901, 3902` all have reward choices —
i.e. essentially the whole chain was unreachable.

`quest_cmd` cannot carry the argument: `bots/lua_bot/intent.nim` validates
`command notin QuestCommands` against exact strings, so `/questreward 1` is
rejected at the boundary. The fix therefore goes through the UI surface the
client already presents: the choice buttons are presented controls with
reference ids `quest-reward:1 .. quest-reward:N`
(`environment/client/ui/quest_frame.nim:624`, drawn from `choiceItems` at
`sourceStart = 1`). Pressing one calls `selectQuestFrameChoice`, after which
the plain `/questreward` reads `selectedChoiceId`.

**Fix.** `reward_choice_reference()` in `accelerated.lua`: on the reward panel,
if `quest_frame.choice_items` is non-empty and `selected_choice` is not already
a valid index, `ui_press` the first available `quest-reward:N`; otherwise send
`/questreward`. Choice 1 is deterministic, not optimal — picking the best item
for the class is a later refinement, noted as a place an LLM planner could
genuinely help (ticket 0054).

## Failure 2 — a finished quest can never be walked back to

**Cause.** The soft-quest path gated *all* questgiver travel behind "nothing
huntable within 40 yards":

```lua
local allowTravel = allow_quest_travel(view) and not nearbyHunt
```

That gate was tuned for a 720s scored grind episode, where walking off to a new
quest costs kills. Applying it to **turn-ins** as well is what strands finished
work: every Deathknell questgiver stands inside a ring of Duskbats, Mindless
Zombies and Rattlecage Skeletons, so `nearbyHunt` is essentially always true in
town and the seat can never walk back to bank an objective it has already
completed. `allow_quest_travel` even had a `has_reward_marker` special case,
but the `and not nearbyHunt` outside it cancelled it.

**Fix.** `quest_step(view, allowTurnInTravel, allowAcceptTravel)` — two
independent gates. Reward markers (rank 0) travel unconditionally; new accepts
(rank 1) keep the level and nearby-pull gates exactly as measured on
2026-08-10. Turn-in travel is still bounded by `QUEST_BUDGET_SECONDS` and
`QUESTGIVER_PATIENCE`, so a giver that will not open still gets abandoned.

## Failure 3 — the bots cannot loot, so no item objective can ever complete

**This is the headline gap the ticket asked about.** `A New Plague` (Tusk,
Beru, `status=3`, `item_count1=0` for days) requires 5x Darkhound Blood; the
item only enters the bags by looting a corpse.

The lua-bot boundary exposes **no loot verb and no loot state**:
`bots/lua_bot/intent.nim` has no loot intent, and `bots/lua_bot/view.nim` never
pushes `lootOpen` / `lootTargetGuid` / loot slots even though
`environment/contract/observation_types.nim` carries them. The RealPlayerBot
policy has a complete loot module (`bots/real_playerbot/policy/loot.nim`,
`handleLootState`), but `pilot.nim` does not import it. In the client the only
loot trigger is the mouse hover/right-click path
(`player/runtime/input.nim`, `movement_actions.nim`), which a headless seat
never exercises.

**It is nonetheless reachable from Lua today, with no fork change**, through
two surfaces that already exist:

1. `/interact <guid>` on a lootable corpse. `defaultInteractionActionKindForUnitObject`
   (`environment/client/client_state/target.nim:400`) returns
   `ClientActionLootTarget` for a `Mob`/`Npc` object whose
   `isLootableUnitObject()` is true, and `ClientActionInteractTarget` runs it
   nested. The `interact` intent already sends exactly this command.
2. The stock LootFrame slot buttons are presented controls with reference ids
   `loot-slot:<targetGuid>:<apiSlot>` and `loot-money:<targetGuid>`
   (`environment/client/ui/loot_frame.nim:165`), so `ui_press` can take them —
   the same mechanism the brain already uses for gossip and greeting rows.

**Fix.** `loot_step()` in `accelerated.lua`: the kill that produced a corpse
arms `lootGuid`; while it is armed the brain presses any enabled `loot-slot:` /
`loot-money:` control it can see, and `interact`s the corpse when the window is
not open yet. Bounded by `LOOT_OPEN_SECONDS` (window never opened) and
`LOOT_EMPTY_FRAMES` (a take is asynchronous, so one empty frame is a pending
slot, not an empty corpse). Gated behind the same `QUESTS` flag as the rest of
the soft-quest path, so the grind-only scored lanes keep the behaviour their
A/B measured.

**The guid in those references must never be compared in Lua.** `view.nim`
pushes guids as `cast[int64](uint64(...))`, so a creature guid with the high
bits set arrives in Lua as a *negative* integer, while the reference id spells
it as an unsigned decimal. Only one loot window can be open at a time, so the
prefix is sufficient identity — matching the guid would silently never fire.

## Failure 4 — a stranded chat edit box freezes the seat permanently

**The worst one, and it hid behind a lie in the status file.** After walking
into the Deathknell church, Kaisel sat at exactly (1837.8, 1630.1, 96.93) for
**six minutes** while `status.json` reported `nav_progress: "following"` the
whole time. Not one yard of displacement. The four home seats' quest work dies
here too — this is the church every Deathknell questgiver stands in.

Diagnosis came from logging the raw view at the wedge:

```
unstick bearing 1 at 1837.8,1630.1 mode=grounded moving=false allowed=true
  rooted=false chat=true/"" dialog=false gossip=false
```

`movement_allowed` true, `rooted` false, `grounded`, no dialog — and
**`chat_input_visible = true` with an empty box.** Every movement key was
going into the chat edit box.

**Cause.** The host drives a slash command over several frames — press Enter to
open the box, send the text, press Enter to submit (`pilot.nim driveChat`) —
and it only advances that sequence while the *same* chat-driven intent comes
back. Return a different intent mid-sequence and the box is left open, and
nothing ever closes it: `driveChat` is the only code that touches it and it is
only called from an intent arm. Every keypress after that is swallowed.

The trigger was our own `QUEST_BUDGET_SECONDS` expiring while `/interact` was
still being typed at Shadow Priest Sarvis (`quest budget exhausted on Shadow
Priest Sarvis` is the last log line before the freeze). Decide fell through to
roam, and the seat never moved again. A wandering mob entering hunt range, a
patience timeout, or a kill landing would all do the same thing.

**Fix.** Re-driving any chat command clears the box (an empty box gets typed
into and submitted; a box holding a different partial command gets Escape), so
decide flushes a *stranded* box with a harmless `/gossip`. Two things matter:

- **Time-gate it.** The first version flushed on sight and cancelled every
  command the brain issued — including its own loot `/interact`, producing a
  perfect thrash loop. A sequence in flight lasts two or three frames;
  `CHAT_STUCK_SECONDS = 4` separates the two cases cleanly.
- **Only when no dialog is open**, so `/gossip` can never be read as a
  greeting-row selection.

**This deserves a fork fix too, and the Lua guard is a workaround.** The host
knows it has a chat sequence in flight (it already tracks exactly that for form
casts: `state.chatCastSpell` + `ChatCastTimeoutSeconds`). `/interact`,
`/questaccept`, `/questcomplete`, `/questreward`, `/release`, `/reclaim` and
`/acceptrez` all drive the box with no such ownership, so any brain that
changes its mind mid-command bricks its own seat. Recommended: give
`libInteract` / `libQuestCmd` / lifecycle commands the same in-flight guard the
form cast has, and close the box on abandonment.

## Failure 5 — the wedge watchdog ate its own loot

Self-inflicted, found and fixed in the same session. Looting holds position by
design (stand on the corpse, press slot buttons), which looks exactly like a
wedge to a watchdog that only measures displacement. The escape leg preempted
`loot_step`, cancelled the `/interact` mid-chat, stranded the box, and the
recovery flush cancelled the next attempt. The watchdog now treats an open
dialog, an in-flight chat command, and an armed loot as *busy* and resets its
anchor instead of firing.

## Constant changes (QUESTS-only, so no scored-lane exposure)

`QUESTGIVER_YARDS` 60 → 120, `QUEST_BUDGET_SECONDS` 25 → 60,
`QUESTGIVER_PATIENCE` 45 → 75. At 60 yards a seat that walks out to a grinding
field can never see town again, and every Deathknell giver is in town; at a 25s
budget every approach longer than a short stroll is abandoned in transit (and,
before Failure 4 was fixed, abandoned *mid-`/interact`*, which is what bricked
the seat). All of it sits behind the `QUESTS` flag the scored lanes keep off,
so the 2026-08-10 A/B baseline is untouched.

## Environment issue seen during the loop (not ours to fix here)

The QA seat froze twice the way `docs/postmortems/2026-08-15-asset-server-connection-drops.md`
describes: `status.json` stops advancing, the launcher process stays alive at
~50% CPU / 2.5 GB RSS, the debug port stops acking, and the log tail is full of
`http fetch failed (Connection was closed before full request has been made)`
on chunk manifests. **This happened with the H1 fix already live** — the
running nginx on 25608 (launch unit `807bb7706ad7`, started 02:52) does carry
`keepalive_requests 100000`. So keepalive exhaustion was not the whole story.
Useful data point for that postmortem's owner. The QA loop worked around it
with a supervisor that restarts the seat when `status.json` goes stale;
restarting a frozen client is supervision, not progress.
